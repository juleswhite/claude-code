# Feature Documentation Generator

Automatically generate complete technical and user documentation for: $ARGUMENTS

## Step 1: Analyze the Feature

1. **Search the codebase** for all files related to `$ARGUMENTS` — components, routes, API endpoints, models, utilities, tests
2. **Classify the feature type**:
   - **Frontend-only**: changes only in components, styles, or client-side logic
   - **Backend-only**: changes only in API routes, models, database, or server logic
   - **Full-stack**: changes span both frontend and backend
3. **Identify**:
   - Entry points (routes, buttons, API endpoints)
   - Data flow (what data moves where)
   - Dependencies (libraries, services, other features)
   - Configuration requirements (env variables, feature flags)

## Step 2: Find Existing Documentation Patterns

1. Check `docs/` directory for existing documentation style and structure
2. If no docs exist yet, create `docs/dev/` and `docs/user/` directories
3. Match the tone, formatting, and depth of any existing docs
4. Collect links to related existing documentation for cross-referencing

## Step 3: Generate Developer Documentation

Create `docs/dev/{feature-name}-implementation.md` with this structure:

```markdown
# {Feature Name} — Technical Documentation

> Auto-generated by document-feature command. Last updated: {date}
> **Feature type**: Frontend / Backend / Full-stack

## Overview
Brief description of what this feature does and why it exists.

## Architecture

### File Structure
- List every file involved with a one-line description of its role

### Data Flow
Describe how data moves through the feature:
1. User action / trigger
2. Frontend handling
3. API request (if applicable)
4. Backend processing (if applicable)
5. Database changes (if applicable)
6. Response / UI update

## API Reference (if backend or full-stack)

### Endpoints
For each endpoint:
| Field       | Value                          |
|-------------|--------------------------------|
| Method      | GET / POST / PUT / DELETE      |
| Path        | /api/...                       |
| Auth        | Required / Public              |
| Rate limit  | If applicable                  |

**Request body:**
```json
{ "example": "payload" }
```

**Response:**
```json
{ "example": "response" }
```

**Error codes:**
| Code | Meaning              |
|------|----------------------|
| 400  | ...                  |
| 401  | ...                  |
| 404  | ...                  |

### Component API (if frontend or full-stack)
For each component:
- Props with types and defaults
- Events emitted
- Slots / children expected

## Implementation Notes
- Key design decisions and why they were made
- Known limitations or trade-offs
- Performance considerations

## Dependencies
- External libraries used and why
- Internal modules this feature depends on
- Environment variables required

## Testing
- How to run tests for this feature
- Key test scenarios covered
- How to test manually

## Related Documentation
- Links to related dev docs
- Link to user documentation: `docs/user/how-to-{feature-name}.md`
```

## Step 4: Generate User Documentation

Create `docs/user/how-to-{feature-name}.md` with this structure:

```markdown
# How to {Feature Name}

> Last updated: {date}

## What This Does
One or two sentences explaining the feature in simple, non-technical language.

## Before You Start
- Any prerequisites (account type, permissions, setup needed)

## Step-by-Step Guide

### Step 1: {Action}
{Clear instruction in simple language}

![Screenshot: {description of what user should see}](screenshots/{feature-name}-step-1.png)
<!-- TODO: Capture screenshot showing {specific UI state} -->

### Step 2: {Action}
{Clear instruction}

![Screenshot: {description}](screenshots/{feature-name}-step-2.png)
<!-- TODO: Capture screenshot showing {specific UI state} -->

### Step 3: {Action}
{Clear instruction}

![Screenshot: {description}](screenshots/{feature-name}-step-3.png)
<!-- TODO: Capture screenshot showing {specific UI state} -->

## Common Issues

### {Problem 1}
**What you see:** Description of the problem
**How to fix it:** Step-by-step solution

### {Problem 2}
**What you see:** Description of the problem
**How to fix it:** Step-by-step solution

## FAQ
- **Q: {Common question}?**
  A: {Answer}

## Need More Help?
- Contact: {support channel}
- Related guides: {links to related user docs}
- Technical details: `docs/dev/{feature-name}-implementation.md`
```

## Step 5: Screenshot Placeholders

For each step in the user guide:
1. Identify the exact UI state the screenshot should capture
2. Write a descriptive TODO comment with specific instructions for capturing
3. Create the `docs/user/screenshots/` directory if it doesn't exist
4. If the project has a testing/screenshot tool, generate capture commands

## Step 6: Cross-Reference

1. Add a link from the dev doc → user doc and vice versa
2. Search existing docs for mentions of related features
3. Add "See also" links in both directions where relevant
4. If a README.md or docs index exists, add the new feature to it

## Output Summary

After generating both files, provide:
- Paths to both created files
- Feature type detected (frontend/backend/full-stack)
- Number of API endpoints documented
- Number of components documented
- Count of screenshot placeholders that need capturing
- List of related docs that were cross-linked
